WEB PROGRAMMING · WEEK 05

JavaScript DOM 與事件處理

不必先背完 DOM 語法。先看懂使用者做了什麼、程式呼叫哪個功能，以及畫面如何改變。

Event→ Function→ DOM Change→ UI Result

01 · LEARNING GOALS

完成本週後，你可以

  • 用 top-down 的方式辨認 `app.js` 的資料載入、畫面 render、狀態更新與事件處理。
  • 追蹤一條完整流程：Event → Function → DOM Change → UI Result。
  • 用 Event、Function、DOM 與預期畫面描述需求，請 AI 協助完成局部修改。
  • 檢查 AI 改了哪些檔案、事件監聽器、DOM 元素與狀態，並確認沒有破壞既有功能。

02 · TOP-DOWN READING

先看程式地圖，再看細節

不熟悉一支 `app.js` 時，不要急著逐行翻譯。先從 function 名稱和呼叫順序猜出責任， 再挑一條互動流程深入追蹤。

資料與初始化

readJson()、validatePageData()、loadPageData()

載入、檢查資料，然後啟動初始畫面。

Render / 建立畫面

renderNavigation()、renderDashboard()、createDashboardCard()

把資料轉成 DOM 節點並放進頁面。

UI 狀態

openSidebar()、closeSidebar()、toggleTheme()

讓側欄、主題或選取狀態切換。

Event / Handler

addEventListener()、handleDocumentKeydown()

把使用者或瀏覽器事件連到對應功能。

閱讀順序

先看 function 名稱 → 找啟動點 → 追一條事件流程 → 最後才看語法細節。

04 · TRY IT

動手追蹤 Event → Function → DOM

操作下面的示範，再觀察按鈕狀態、文字和畫面 class 如何改變。

模擬側邊欄

按 Escape 或關閉按鈕，追蹤共用的關閉 function。

提示：先操作，再說明發生了什麼。

等待操作。試試開啟選單，接著按 Escape。

觀察問題
  1. 哪個 Event 被觸發？
  2. Event listener 呼叫哪個 Function？
  3. Function 修改了哪些 DOM 屬性或文字？
  4. 畫面結果是否符合預期？

05 · PROMPT DESIGN

把互動需求說清楚，再請 AI 寫程式

只說「幫我加 ESC 關閉」資訊不足。提供流程和修改限制，AI 才容易做出小而可檢查的改動。

目前已有 openSidebar() 和 closeSidebar()。

需求：
Event：使用者按下 Escape。
Function：沿用 closeSidebar()。
DOM Change：沿用 closeSidebar() 既有操作，不重複寫 DOM 修改。
Expected UI：側邊欄關閉，按鈕的 aria-expanded 回到 false。

限制：
1. 只修改必要的 JavaScript。
2. 不要重寫整份 app.js。
3. 不要改變其他側邊欄操作。
4. 完成後列出 Event → Function → DOM → UI Result。
修改既有功能時

先描述目前行為，再說明想保留什麼、要改什麼，以及哪些程式碼不可動。

06 · DOM & EVENTS

本週先認識常用的 DOM 變更

目的常見寫法需求描述方式
更新文字element.textContent = "完成";把提示區文字改成完成。
切換樣式element.classList.toggle("active");按一下切換 active class。
更新狀態element.setAttribute("aria-expanded", "true");展開時同步更新無障礙狀態。
隱藏或顯示element.hidden = true;收合時隱藏說明區。
新增節點list.append(item);按 Add 時新增一個清單項目。
重新 rendercontainer.replaceChildren();重畫之前先清除舊卡片。

常見 Event：click、input、change、submit、keydown。

07 · DEBUGGING

互動沒反應時，依序檢查四層

  1. Element：程式有沒有取得正確的 DOM 元素？
  2. Event：listener 有沒有綁定？事件真的有發生嗎？
  3. Function：handler 有沒有執行？需要時用 console 訊息追蹤。
  4. DOM / CSS：DOM 值有沒有改？CSS 有沒有定義對應狀態？
預期：#menuToggle click → openSidebar() → #sidebar 加上 is-open

若無效，檢查：
1. #menuToggle 和 #sidebar 是否存在
2. click listener 是否綁在正確元素
3. openSidebar() 是否執行
4. is-open 是否加到 sidebar
5. CSS 是否有對應 .is-open 樣式

08 · PRACTICE & REVIEW

練習：先描述，再實作與驗收

練習 1：按 Escape 關閉 Sidebar

Event：document keydown；Function：沿用 closeSidebar()；驗收：側欄關閉且 Menu 按鈕狀態正確。

練習 2：導覽項目預覽說明

Event：mouseenter / focus；Function：showNavigationPreview(item)；DOM：更新預覽文字。

練習 3：選取 Dashboard Card

Event：卡片 click；Function：setSelectedCard()；DOM：同一時間只有一張卡有 selected 狀態。

練習 4：更新提示文字

Event：更新按鈕 click；Function：changeMessage()；DOM：更新提示區的 textContent。

練習 5：展開或收合詳細面板

Event：按鈕 click；DOM：切換 detail 的 hidden，並同步按鈕的 aria-expanded。

每次 AI 修改後，回答這五題

  1. Event 是什麼？
  2. Listener 綁在哪個 DOM element？
  3. 觸發哪個 function？
  4. Function 修改哪些 DOM、class 或 attribute？
  5. 這個修改會不會影響既有功能？

09 · AI CODING WORKFLOW

Describe → Ask AI → Inspect → Run → Verify → Refine → Commit

  1. Describe：先列出 Event、Function、DOM 與預期畫面。
  2. Ask AI：提出清楚需求，指定要沿用的 function 與修改限制。
  3. Inspect：看 diff，確認改動範圍和 DOM 目標。
  4. Run：在瀏覽器實際操作，不只看程式碼。
  5. Verify：確認 Event、Function、DOM 與 UI 都符合預期，也測試原有行為。
  6. Refine：描述具體問題，要求 AI 做最小修正。
  7. Commit：用功能描述作為提交訊息，例如 Add Escape key sidebar interaction。
提交前檢查

確認變更只包含本次功能，不要提交 `.env`、密碼或真實個人資料。
